### 更新与缓存的现状

`updates.py::_download_package` 按发布清单下载完整安装 EXE 或免安装 ZIP并校验完整长度/SHA；目前没有二进制差分或分块增量协议。安装版的更新器运行新安装程序覆盖同一安装目录；免安装版解压到新的相邻目录，保留旧 EXE。用户可在应用内完成下载和换版，无须每次手动处理所有步骤，但网络传输量仍是完整包。

`startup_cache.py::prepare` 按内容身份复用科学、宿主、应用三类运行缓存，未变化的大组件无需重新展开。它只回收中断的 staging，并不自动按历史版本回收所有旧 `apps/host/science` 身份。升级不会导致这些目录失去归属，但改变过的组件缓存可能累积。设置中的清除全部缓存会安全退出后清理，安装版卸载同样调用清理；活动实例会阻止删除。此操作也清理可重新计算的内部结果副本，需先导出需要保留的结果；设置、原始资料、录音、工程和正式导出保留。

更新下载/辅助进程目录有按登记身份和首次发现时间计算的 7 天回收策略，应用运行期间每小时维护，正在应用或来源未确认的目录保留。MFA 已安装组件、模型及选择的外部环境不属于上述启动缓存，当前不会随主程序更新或清缓存自动删除。

### 建议的后续方向（未实施）

优先设计按组件内容摘要下载的更新：小型应用包 + 共用宿主包 + EGG/LPC 包 + 唇形包 + 说明书媒体包。每次只传缺失或内容变化的组件，保留完整离线包作为备选。该方式适合现有内容身份结构，比直接对整份 solid 压缩 EXE 打差分更容易维护；仍需调整当前宿主与科学段共享关系、签名/摘要、失败回滚与下载准入，不能只把 ZIP 移出 EXE。

同时建立组件引用关系和保留策略，保护当前使用及必要回滚版本，成功更新且无进程占用后再回收无引用内容。只有修改应用、安装器、更新服务并做最终字节验收后，才可承诺实际净减量、增量下载或自动回收。当前用户请求为可行性咨询，尚未实施该架构变化。
